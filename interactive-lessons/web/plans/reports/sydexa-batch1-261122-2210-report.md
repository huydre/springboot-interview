## 1. Per-lesson summary

### L1 index-and-btree (about 25k chars, 11 parts + 10-question exam)
Structure: hero with video (0:46) -> Quick Quiz #1 before any teaching (hook: "CREATE INDEX made it 4000x faster, what changed?") -> "Lo trinh" roadmap (3 chang) -> 11 parts, each opened by a short video (0:00/0:00 player) and closed by a 1-question Quick Quiz -> "Du doan truoc khi xem" (predict-before-you-see) quizzes before 2 widgets -> Part 11 hands-on real PostgreSQL 17 sandbox ("Start Practice", 4+ guided steps, user creates 3 indexes and compares sizes) -> 10-question whole-lesson exam with explanations -> "Tong ket" with a one-line journey recap + 7 flip cards ("click to flip") -> next-lesson preview + "Da hoan thanh" button.
Widgets:
- Race "Full Table Scan vs Index": learner picks table size (10k/1M/10M rows) and match position (row 5, middle, last, absent), presses "Chay dua"; two lanes count pages read (10,000 vs 4). Teaches: without UNIQUE/LIMIT 1 the scan cannot stop at row 5. Preceded by an explicit "answer in your head first" prompt.
- Sorted-array insert: button "Insert 18" shifts cells right one by one; shows O(n) write cost. Preceded by a predict quiz.
- Leaf-node anatomy ("Ban mo Leaf Node"): page size (8KB PG / 16KB InnoDB) x key type (INT 4B, BIGINT 8B, UUID 16B, VARCHAR 30B) x rows (1M/10M/100M) -> entries per page (737), fanout, tree height (3), BST would need 27 reads. Causal chain printed: bigger key -> fewer entries/page -> lower fanout -> more levels -> more disk reads. States model simplification honestly (key + 16B pointer).
- Doubly linked list insert: "Insert Node" animates cutting/relinking two pointers (O(1)).
- "Physical chaos, logical order": INSERT 1 row / insert 10; heap grid fills in insertion order while index column stays A-Z; two read heads run in index order vs physical order and report random vs sequential I/O gap.
- B-Tree build bottom-up: "Xay B-Tree" animates leaves -> branch (max key per leaf) -> root.
- B-Tree traversal: pick key (57, 13, 35, 95, 50 absent), "Search" highlights only the path, others dim; step-by-step text (3 blocks).
- B-Tree insert 18: predict quiz (how many blocks written: exactly 1), then "Insert 18" shows root->branch->leaf path.
- Range query B+Tree vs B-Tree: one button runs both trees, counter "nodes visited" (7 vs 15). Predict quiz first.
- Table B-Tree vs B+Tree (linked list, data location, internal content, height, range, who uses it) + note that docs say "B-Tree" but mean B+Tree.
Facts: HDD ~100,000x slower than RAM; read unit is page (4/8/16KB); CREATE INDEX does not reorder the table, builds a separate sorted structure with ROWID/ctid; index is redundancy that costs space + write speed; BST wastes 99.9% of a page and needs log2 n reads; sorted array insert O(n); leaf = hundreds of sorted keys; leaves linked both ways (range scans, DESC with the same index, O(1) leaf insert); index order != heap order -> random I/O, why large result sets prefer full scan; 500^3 = 125M rows in 3 reads, root is cached so often 2 reads; 10x data -> still 3-4 reads; pure B-Tree stores data in every node, B+Tree only in leaves.

### L2 index-in-practice ("Cai gia cua Index", about 12.5k chars, 5 parts)
Structure: story hook ("Monday index made 8s -> 2ms, Friday INSERT 500ms, 7 indexes") -> Warm-up quiz on previous lesson (B+Tree data location, 2 questions) -> roadmap (3 bullets) -> Part 1 three steps of index lookup -> quiz -> Part 2 "when the guide betrays you" (myth "index is broken, REBUILD") -> quiz -> Part 3 cost / why not index everything -> quiz (5 indexes = 6 structures) -> Part 4 exercises (drag-to-build B-Tree + PG sandbox) -> Part 5 final 3-question check + flip card + "big picture" recap of both lessons -> next-lesson teaser phrased as a question ("same = but 0.01 ms vs 12 ms, why?") -> prev/next buttons.
Widgets:
- "3 steps of Index Lookup, find key 57": button "Buoc 1/2/3" steps the highlight (tree traversal -> leaf chain -> jump to table heap) with a "Block reads" counter. Teaches which step is bounded and which is the killer.
- Code cards with real EXPLAIN output for Index Only Scan / Index Scan / Bitmap Heap Scan, each with a line-by-line reading (cost 4.44 -> 8.44 and width 32 -> 128 = the price of table access).
- Chart "which strategy wins" (x = % rows returned, y = time; Index/Bitmap/Seq crossing points) with note that crossovers depend on random_page_cost, storage, correlation. Static chart, no inputs.
- Drag-and-drop exercise "build B-Tree from dataset": drag 12 numbers into 4 leaf slots, then branch = max key per leaf, then trace key 35 and a duplicate key 27.
- PG 17 sandbox (shared component with L1).
- Flip cards for recap.
Facts: lookup = traverse (O(log n), bounded, 3-4 reads) + leaf chain (O(k)) + table access (O(k) random I/O, the killer); Index Only Scan skips step 3; Bitmap scan turns random heap I/O into physical-order I/O; optimizer picks by statistics, skips index around >5-10% of rows (status='ACTIVE' 80%, gender 50%); B-tree never skews, what happens is bloat (page splits, dead tuples under MVCC), so "REBUILD" is rarely the answer; write cost = 1 table + N trees; golden rule index only WHERE/JOIN/ORDER BY columns; 12 indexes -> INSERT 5 -> 200 ms, drop to 4 -> 15 ms; interview answer in 3 points (space, write cost, optimizer may ignore); tree depth 4 = 4 + 1 table read = about 5 blocks.

### L3 where-clause-equality ("Equality & EXPLAIN Plan", about 14k chars)
Structure: hero video (0:34) -> roadmap (3 chang) -> Nen tang + PK lookup (recap video, employees DDL, "mission: find guy 123", three-step walk) -> quiz -> "Reading EXPLAIN" (EXPLAIN vs EXPLAIN ANALYZE, danger note: ANALYZE runs DELETE for real, wrap in BEGIN/ROLLBACK; annotated plan table; BUFFERS trick) -> quiz -> UNIQUE vs RANGE scan comparison table -> quiz -> Case study (merger, PK reordered to (subsidiary_id, employee_id), query by last_name hangs) with 3 numbered lessons -> statistics ("the general holding an outdated report", run ANALYZE after bulk loads) -> quiz -> mental-model flowchart + 3-question checklist -> PG sandbox lab (100K rows with/without index) -> 4-question exam -> flip cards -> teaser.
Widgets:
- INDEX UNIQUE SCAN animation: button "Tim 123" walks root -> internal -> leaf -> table block, highlighting the path and the matching table row.
- "Logarithmic power" tree-of-squares graphic: 300 keys per node, 4 steps for 8 billion rows (static, with level labels).
- Flowchart with "Animate" button: WHERE col = ? -> has index? -> UNIQUE? -> Seq / Unique / Range scan, nodes light up in order.
- Sandbox lab and flip cards.
Facts: PRIMARY KEY auto-creates a unique B-tree; unique scan stops after 1 entry (no leaf chain), ~4 buffer hits regardless of table size; non-unique index with = still does a range scan (reads one more entry to be sure) because the DB trusts the structure, not the data; cost is an internal unit not ms; read the plan columns: Index Cond, estimated vs actual rows, Planning/Execution time; BUFFERS "shared hit=4" is the stable metric (time is noisy); the plan operation name can be identical for the 5-row and the 100,000-row plan, so read Rows; wrong index (leading column low-selectivity) can be slower than seq scan; fix = create the right index, not hints; stale statistics cause wrong choice; ANALYZE after bulk import.

### L4 concatenated-indexes ("Composite Index & thu tu cot", about 22k chars)
Structure: hero video (1:23) with a hook quiz right after it (phone book sorted by (last, first), you only know the first name) -> roadmap -> story continues from L3 (employees PK (employee_id, subsidiary_id)) -> DB-name translation table (Index Scan / ref,range / Index Seek / INDEX RANGE SCAN across PG, MySQL, SQL Server, Oracle) -> "how composite index sorts" (priority table + phone book + 3-column orders example with sorted sample rows + ORDER BY DESC reuse via linked list) -> quiz -> Leftmost Prefix "ladder" metaphor -> animation -> usable/unusable list -> real plan reading (Seq Scan + Filter) -> access vs index-filter predicate (and the PG trap that both appear under "Index Cond") -> quiz (A,C,D skipping B) -> "stop at first range" -> "equality first, range last" with good/bad index DDL -> quiz -> reorder-columns side effect (employee_id query becomes Seq Scan) -> quiz -> 4-step rule for choosing column order -> applied quiz (3 product queries) -> "look back" recap + teaser (covering index) -> 5 flip cards. No sandbox here.
Widgets:
- "Leftmost Prefix Rule" B-Tree animation, one "Bat dau" button: runs two searches on a 3-column tree (A,B,C triples in leaves A=1,2,3) to compare WHERE A=.. against WHERE B=.. (first narrows to one leaf, second must visit every leaf).
- Everything else is static text/tables/code; heavy use of the ladder and phone-book metaphors and 6 quick quizzes.
Facts: composite index = one B+Tree sorted by col1, then col2 within equal col1, then col3; col2 is only locally sorted; leftmost prefix; skipping a middle column (A,C) makes C an index filter, not an access predicate; first range (>, BETWEEN, LIKE 'abc%') ends narrowing for later columns; rule "equality first, range last"; PG "Index Cond" hides the access-vs-filter difference, you compare to the index definition yourself; Skip Scan exists (PG 18, MySQL 8.0.13, Oracle) and only pays off for low-cardinality leading columns; reordering columns can silently break other queries; choosing order by reuse across query patterns, NOT by "most distinct column first" (myth rejected: when all equality columns are present the order does not change tree-walk cost); DESC served by backward walk; composite is different from two single-column indexes.

### L5 slow-indexes ("3 chien thuat Scan + 6 Red Flags", about 12.9k chars)
Structure: police-chief analogy hook (knock every door / GPS / narrow to a district) -> roadmap + explicit "principles are engine-agnostic, names differ" note -> Bitmap Scan explained in 2 steps (+ note: PG-only name, MySQL closest is Index Merge) -> video -> quiz -> "which wins" chart -> anatomy of a plan (cost, rows est vs actual, actual time, loops, planning/execution) -> quiz -> PG keyword cheat sheet (Index Cond, Filter, Rows Removed by Filter, Seq/Bitmap/Index Only Scan, shared hit vs read) -> cross-engine translation table (PG / MySQL / SQL Server / Oracle, 7 rows) -> quiz -> 6 Red Flags -> quiz -> "healthy plan" checklist -> teaser (function/expression index) -> 6 flip cards. No sandbox, no custom widget.
Widgets: only the static "which strategy wins" chart (x = % rows, y = time; 3 curves with labelled winning zones) and a styled "Loops Trap" callout (0.05 ms x 10,000 = 500 ms). Presentation is mostly tables and one-line fixes per red flag.
Facts: Bitmap Index Scan marks pages, Bitmap Heap Scan reads them in physical order; est vs actual rows far apart means stale stats (ANALYZE); Rows Removed by Filter large = wasted I/O, move predicate into the index; seq scan fine for small tables or when returning most of the table; loops x actual time = real time (actual time is per loop); Sort Method "external merge Disk" means work_mem exhausted (SET work_mem or reduce data); index cost > seq cost = low selectivity; shared hit vs shared read (8KB blocks); 4-step engine-independent debug routine: plan, est vs actual, wasted reads, spills.

### L6 function-and-expression-index ("Khi Function pha Index", about 16.8k chars)
Structure: hook = two queries with identical result, 3 ms vs 4200 ms (hero video 2:07) -> quiz (which query can use the email index) -> roadmap -> 6-pattern gallery of index-breaking predicates (UPPER, EXTRACT, amount*1.1, COALESCE, ::date, ::integer) with "index on X, query on f(X)" caption -> rewrite catalogue (5 before/after pairs with red/green marks) incl. caveats (LIKE 'p%' needs C locale or varchar_pattern_ops; moving arithmetic right only works if the right side has no column) -> sandbox "rewrite and compare plans" -> quiz -> video on expression index -> quiz (UPPER(name) index vs LOWER query) -> expression index syntax and demo plan, with honest note that rewriting beats it for EXTRACT -> case-insensitive options table (LOWER index, CITEXT, nondeterministic collation, ILIKE) -> ORM warning (Hibernate/Spring Data use LOWER, Django UPPER, so team convention in 3 lines) -> quiz -> deterministic rule (IMMUTABLE / STABLE / VOLATILE; lying about IMMUTABLE corrupts silently) -> sandbox with 3 scenarios (AGE blocked, lie accepted, correct function) -> quiz -> over-indexing video + quiz (50k inserts/s, 15 indexes) -> write-cost checklist (INSERT / DELETE+VACUUM / UPDATE and HOT) -> 5 questions before creating an index -> two ready monitoring queries over pg_stat_user_indexes (list, idx_scan = 0) with caveats -> zoom-out recap -> 8 flip cards.
Widgets: no custom animation; three PG sandboxes (rewrite lab, deterministic lab) and 7+ quizzes. Teaching value comes from before/after code pairs, the "optimizer sees a BLACKBOX" mental model and failure-driven labs (the DB refusing the index, then the DB being lied to).
Facts: function on the column = non-SARGable = seq scan; fix 1 rewrite to bare column vs range/constant; fix 2 expression index, query expression must match index expression exactly; expression index stores the function result at write time so it must be IMMUTABLE; PG only checks the declaration, not the body; HOT update skips all index writes when no indexed column changes and page has room; DELETE defers index cleanup to VACUUM; idx_scan = 0 candidates to drop but PK/UNIQUE indexes show 0 and must stay; stats reset on crash or pg_stat_reset().

### L7 bind-variables-plan-caching ("Plan Caching & SQL Injection", about 14k chars)
Structure: two-part incident story as the hook (2 AM CPU 98% because of literals; a week later "6th execution 3 ms -> 280 ms", hero video 1:02) -> roadmap -> pipeline video (Parse, Analyze, Rewrite, Plan, Execute) + quiz -> "10,000 plannings for one dish" video + quiz -> custom vs generic plan (skewed orders.status 95/5 worked example, 5-execution rule, 10% margin rule, invalidation by ANALYZE/DDL, "why a seq scan for 5% is bad") + quiz -> practical fixes (plan_cache_mode, DEALLOCATE+PREPARE, pg_prepared_statements generic_plans/custom_plans PG14+) -> two exceptions where literals are better (skewed small enum, LIKE patterns) -> cross-engine table (PG, Oracle bind peeking + ACS, SQL Server parameter sniffing + PSP, MySQL no global cache) -> injection video + quiz -> sandbox lab (injection, plan caching, custom vs generic, with an honest disclaimer that the Neon HTTP pooler cannot show the counters) -> 6-point recap (includes simple vs extended protocol: psycopg2 client-side escaping vs psycopg3/JDBC server-side bind) -> 6 flip cards.
Widgets: no custom animation (4 videos + 1 sandbox + quizzes). The "not a bug in your SQL, a sandbox limitation" disclaimer is a trust-building pattern.
Facts: pipeline of 5 steps, planning is the expensive one; literals = one plan per distinct value; PREPARE skips parse/analyze/rewrite and can cache; first 5 executions custom, then generic if cost < 110% of average custom cost; generic plan is one plan for all values and can hurt rare values on skewed columns; fixes as above; parameterization both reuses plans and separates code from data (injection); Oracle/SQL Server peek the first value (first-use trap), PostgreSQL avoids it with 5 custom runs but keeps only one generic plan; JDBC/extended protocol binds server-side.

### L8 range-queries ("Range, LIKE & Bitmap Combine", about 11.8k chars)
Structure: 5-question warm-up on earlier lessons (first question: 3-column index, which columns are access predicates) + "if you miss some, this lesson clarifies them" framing -> recap video -> quiz (BETWEEN walks the leaf list) -> "which column first" video + quiz (equality first) -> "execution plan proves it" (two plans with identical Index Cond, Buffers 23 vs 4) -> myth-busting "most selective first" with the exact exception rule: equality present = equality first; all-range = most selective first -> sandbox (2 index orders, compare Buffers) -> "numbers to strings" video + quiz (which LIKE can use index) -> LIKE table (WI%ND scans ~18 entries, WIN%D ~2, WINA% ~1, %NAND whole index) -> LIKE + bind params trap (generic plan cannot extract prefix, seq scan) with 3 workarounds (manual range >= $1 AND < $2, force_custom_plan, LIKE $1 || '%') -> two range conditions (B-tree is 1-D, only one access range) -> options: composite with one filter vs two indexes + BitmapAnd/BitmapOr (exact vs lossy bitmap, Recheck Cond, work_mem) -> real story (Mattermost, MySQL index-merge picked over a composite index, 195K estimated vs 13M actual rows, fixed with USE INDEX; PG equivalent: pg_hint_plan, SET enable_*) -> sandbox 2 -> quiz -> video -> 2 closing quizzes -> 5 flip cards.
Widgets: none custom; 2 PG sandboxes, 4 videos, 6 quizzes. Strong evidence-driven pattern: same Index Cond text, different Buffers, so the learner sees the invisible difference.
Facts: range scan = descend once, walk leaf list; first-range-stops rule; column order criterion is equality vs range (not selectivity), except all-range; LIKE 'abc%' becomes a range, leading wildcard does not; longer prefix = narrower scan; generic plans cannot derive LIKE prefix range; B-tree supports one range access condition; Bitmap combine is rarely better than a well-designed composite index; Bitmap Heap Scan with one index is normal.

## 2. Presentation patterns worth copying (not used by us yet, or used rarely)

Our section model already has `predict`, `quiz`, `takeaway`, `trap`, `cards`, `sql-lab`, step-through widgets, and info-board cards (grep of `src/data/types.ts`). 4. Teaser phrased as an open question at the end ("same = but 0.01 ms vs 12 ms, why?") plus one-line journey recap ("from slow query -> disk I/O -> ... -> B+Tree"). We end with modelAnswer and cards only.
5. Evidence pairs: identical plan text, different Buffers (23 vs 4); same operation name with 5 vs 100,000 rows. Teaches "read numbers, not node names". Our plans show costs but never EXPLAIN (ANALYZE, BUFFERS).

7. Honest model/limitation notes next to widgets ("model is simplified, the relations matter" in fanout; "sandbox cannot show generic_plans counter"). We do this in part; keep doing it.
8. Failure-driven labs: let the DB refuse (AGE() not IMMUTABLE), then lie to it, then do it right. Fits `sql-lab` with `verify`.
9. Drag-to-build exercise (12 numbers into 4 leaves, then branch = max key per leaf, trace key 35, trace duplicate 27). We have btree-search (read-only); a build-from-bottom exercise is a different skill.
10. Sort-by-priority visual: 3-column sample rows sorted by (user_id, status, created_at) shown as a table so the learner sees col2 only sorted within col1 groups.
11. Per-part short quiz after every part (L1: 11 parts, 11 quizzes) plus a 10-question end exam with explanations. We use 1 quiz per section.

## 4. Five new widget ideas (small React widgets, same style as scan-race/fanout)

1. heap-order-widget ("Index order vs table order"). Shows: a 5x8 grid of heap blocks filled in insertion order (random-looking keys) next to a sorted index column. Inputs: slider "percent of rows returned" (0.1 to 100) and toggle "table sorted by this key / insertion order". Output: counters for index scan (random jumps), bitmap (blocks touched in order) and seq scan (all blocks), highlighting the crossover where seq scan wins. Fits: index.ts `no-index` (Phan 4) and sql-optimize `scan-types`. Closes gap 5.
2. composite-ladder-widget ("Access vs filter"). Shows: 30 sorted rows of index (A, B, C) in a table. Inputs: per column a 3-way toggle (not used / equals / range). Output: rows in the scanned contiguous interval shaded, rows that match shaded green, counters "entries scanned / matched", and a label per column (access, filter, ignored). Demonstrates first-range-stops and A+C. Fits: index.ts `composite` (next to leftmost-prefix) and sql-optimize `composite-fk`. Closes gap 8.
3. sargable-rewrite-widget ("Keep the column bare"). Shows: a sorted key line of dates/emails. Inputs: pick a predicate (EXTRACT year, ::date, amount*1.1, LOWER(email), LIKE 'ab%', LIKE '%ab') and a fix (rewrite / expression index / none). Output: with a bare column a single interval is highlighted; with a function every key is crossed through ("computed per row") and the plan label flips Seq Scan to Index Scan, plus the rewritten SQL. Fits: sql-optimize `index-not-used`. Closes gaps 3 and 4.
4. plan-cache-widget ("Executions 1 to 8 of a prepared statement"). Shows: a timeline of EXECUTE boxes with plan type (custom or generic), estimated cost and time. Inputs: buttons "EXECUTE pending" / "EXECUTE completed", toggle plan_cache_mode (auto / force_custom), table skew (95/5). Output: runs 1-5 custom with different plans; from run 6 compares generic cost to 110 percent of the custom average, flips to generic, and 'pending' becomes slow; force_custom keeps it fast and shows the planning-CPU price. Fits: NEW sql-optimize section `plan-cache`. Closes gaps 1 and 2.
5. index-write-cost-widget ("What one write touches"). Shows: the heap plus N small B-tree icons. Inputs: slider number of indexes (0 to 12), operation INSERT / UPDATE indexed column / UPDATE non-indexed column (HOT on/off if page full) / DELETE. Output: pulses on every structure written, a write-cost bar, and a note on VACUUM debt for DELETE. Fits: index.ts `cost` and sql-optimize `index-cost`. Closes gap 9.
(Cheap extras that need no new widget: loops x actual time calculator as a `quiz` with a numeric trap; IMMUTABLE yes/no drill using the existing yes-no-drill component; cross-engine table using `cheat`.)
