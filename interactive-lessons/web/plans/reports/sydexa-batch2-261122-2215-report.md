### L9 partial-index-and-null ("Partial Index & Bay NULL", about 10k chars, 2 parts)
Structure: 2-riddle hook with "answer both and you may skip this lesson" (800MB index for 1000 live rows of 10M; `bonus != 0` returns 500 not 700) -> roadmap (2 parts) -> Part 1 partial index (full vs partial DDL, "small in 2 dimensions", match rule, prepared-statement caveat, 3 DDL examples, criteria) -> Quiz 1 -> "small challenge" predict block (index `WHERE status != 'inactive'`, does a NULL row enter?) -> Part 2 NULL ghost (`!=` drops NULL, NOT IN + NULL = empty, fixes) -> Quiz 2 (the bonus count) -> 6 flip cards -> 2-point summary + "looking back" + teaser (obfuscated conditions).
Widgets: none custom (no SVG animation). Only code blocks with copy button, 2 quizzes, one predict question styled as "Thu doan xem", flip cards. The hook riddles are the presentation device.
Facts: partial index = CREATE INDEX ... WHERE; shrinks vertically (fewer rows) and horizontally (drop the constant column, `processed` always 'N'); table keeps growing while the queue index does not; query WHERE must imply the index WHERE, constant not bind parameter; with PREPARE: custom plan (first 5 runs) can match `processed = $1`, generic plan (6th on) cannot, so "fast then slow"; WHERE may only use IMMUTABLE expressions (NOW() refused at CREATE INDEX); use when repeated queries hit under 10-20% of rows; patterns queue / soft delete (`deleted_at IS NULL`) / status IN (...). NULL = unknown, not empty/zero; WHERE keeps only TRUE so `!= 'paid'` drops NULL rows, and a partial index `WHERE status != 'inactive'` silently excludes NULL rows too (the "bug partial index cannot save you"); NOT IN (1,2,NULL) = id != 1 AND id != 2 AND id != NULL = UNKNOWN, so zero rows; use NOT EXISTS or filter IS NOT NULL in the subquery; declare NOT NULL whenever possible (also helps optimizer); NULLs are indexed in PG, IS NULL / IS NOT NULL can use Index Scan.

### L12 clustering-data-index-filter-and-index-only-scan ("Index Filter & Index Only Scan", about 11k chars)
Structure: hook "index used, still 2.3 s, who is lying" -> warm-up quiz (rows x loops) -> "3 kinds of predicate" via video + 3-question quiz (which is most expensive) -> "when index filter becomes a weapon": LIKE '%SYDEXA%' story with 3 index scenarios A/B/C (numbers: 333 entries in range, 316 filtered, 17 kept) -> quiz -> Index-Only Scan video + quiz (signal = `Heap Fetches: 0`) -> "4-basket recipe" diagram -> quiz (category_id, price ORDER BY LIMIT 50) -> zoom-out with a Before/After counter (333 random I/O -> 0) and 5 points -> 8 flip cards -> bridge teaser (table that IS the index).
Widgets:
- "Leading wildcard paralyzes B-tree" SVG: a row of leaf entries sorted A..V (Anh, Bao, Cuong...), `LIKE 'SYD%'` shows a bracket starting at S, then the `%SYD` case shows "?" over every entry (index does not know where to start). Static.
- "4-basket formula" SVG: a query on top, 4 baskets (1 Equality -> key #1 access, 2 Range/Sort -> key #2 and sort free, 3 non-access WHERE like LIKE %x% or expressions -> index filter, 4 SELECT-only columns -> INCLUDE) and the resulting `CREATE INDEX idx_orders_cover ON orders (customer_id, created_at) INCLUDE (order_id, total_amount, status)`. Static, but it is the main takeaway visual.
- Three videos (3 predicates, index-only scan, one more); no sandbox in this lesson.
Facts: every `Index Scan` hides three predicate roles: access (narrows leaf range), index filter (evaluated at the leaf, no heap), table filter (after fetching the row, most expensive, up to 100x spread); EXPLAIN merges them; leading wildcard cannot be an access predicate but can still be an INDEX filter if the expression and the needed columns are in the index; scenario A (only subsidiary_id) = 333 heap fetches, B (add UPPER(last_name) without INCLUDE) still 333, C (+ INCLUDE first_name, last_name, salary) = 0 heap fetches, Index Only Scan; "clustering data" = putting everything the query reads on the leaf; rule "extend an existing index rather than create a new one" (adding a column after the access predicate is nearly free for scan range, costs a bit of space); `Heap Fetches: 0` is the confirming signal (and needs a fresh visibility map, ie VACUUM); recipe: equality columns first, then range/sort, then filter-only columns (expression, LIKE '%x%'), then INCLUDE for SELECT-only columns; one index gives sorted output (no Sort), index-only scan and LIMIT early stop; INCLUDE is cleaner than making value columns part of the key; design for WHERE and ORDER BY first, add INCLUDE only when Heap Fetches > 0; after a range, later columns are demoted; 3 questions to ask of every plan: which column is access, which is filter, how many heap fetches.

Facts: CREATE INDEX makes a separate B-tree file with its own size and upkeep; one DML = 1 + N writes; sequential keys split only at the edge, random UUIDv4 keys split everywhere; in-place engines write only indexes containing the changed column; PG copy-on-write creates a new tuple so every index needs a new entry unless HOT (same page, no indexed column changed, room on the page, `fillfactor` below 100 helps); PG has no per-index write counter (pg_stat_user_indexes counts reads), measure via pg_stat_user_tables (n_tup_upd, n_tup_hot_upd, n_tup_newpage_upd on PG 16+) and pg_statio_user_indexes; InnoDB metrics `index_page_splits` via `innodb_monitor_enable = 'module_index'`; MVCC DELETE only marks the row (dead tuple / delete-mark / ghost record), cleanup (VACUUM / purge) frees space for reuse but does not shrink the file; partial index only pays off when the filter keeps under 10-20 percent of rows and also spares writes of non-matching rows; INCLUDE puts non-key columns only on leaves, composite-key workaround on MySQL/Oracle; bulk load: building an index once from existing data beats maintaining it row by row; hot columns (counters, balances, stock) should not be indexed, use cache or summary tables; unused-index audit per engine, PK/UNIQUE excluded.

## 4. Five new widget ideas (simple React, same style as scan-race / covering-index-widget)

1. predicate-roles-widget ("Access, index filter, table filter"). Shows: 12 leaf entries of index `(subsidiary_id, [UPPER(last_name)])` as a strip and a heap box below. Inputs: 3 radio buttons for index design A (only `subsidiary_id`), B (+ expression in key), C (+ INCLUDE columns); optional LIKE pattern toggle `'SYD%'` vs `'%SYD%'`. Output: the leaf range bracket (access), entries crossed out at the leaf (index filter), arrows to the heap for table filter, counters "heap fetches 333 / 333 / 0" and the plan label (Index Scan vs Index Only Scan). Fits: index.ts `covering`. Closes gap 5.
2. order-match-widget ("Does this index give ORDER BY for free?"). Shows: a small sorted index table (priority, created_at, name with a NULL) plus a read arrow forward or backward. Inputs: ORDER BY builder (column order, ASC/DESC per column, NULLS FIRST/LAST) and index definition builder with the same controls, LIMIT 5 toggle. Output: green "Index Order Scan, reads 5 entries" or red "Sort node, reads all N rows" with the mismatching dimension highlighted (column / direction / NULL), and a "rows read" counter. Fits: sql-optimize `scan-types` (ORDER BY và Sort) and index.ts `composite`. Closes gaps 7 and 8.
3. join-algorithm-race-widget ("Same join, three algorithms"). Shows: two small tables with 8 and 40 rows, three lanes (Nested Loop, Hash Join, Merge Join) each with a comparison counter and a simple visual (nested pointers, buckets, two pointers). Inputs: toggles "index on inner join column", "inputs already sorted", "work_mem small (spill)" and operator selector (`=` vs `>=`). Output: counts and a disabled lane with the reason (Hash cannot do `>=`; spill shows Batches=4 and extra disk reads). Fits: sql-optimize `join-methods`. Closes gaps 1, 2.
4. write-cost-playground-widget ("What one write touches"). Shows: heap block plus N index icons, a counter of structures written. Inputs: number of indexes (0-8), statement INSERT / UPDATE indexed column / UPDATE non-indexed column / DELETE, engine toggle "in-place (InnoDB, Oracle) vs PG copy-on-write", HOT on/off (page has room). Output: pulses on every touched structure, write amplification 1+N, dead tuple counter for DELETE/UPDATE and a note "VACUUM must clean N indexes". Fits: sql-optimize `index-cost`. Closes gaps 13, 14. (Same idea as batch-1 widget 5 but with the HOT and copy-on-write toggle and Sydexa's cost-playground sliders.)
5. keyset-bookmark-widget ("Why the bookmark needs a tiebreaker"). Shows: 8 rows with 5 sharing identical `created_at`, page size 3. Inputs: toggle bookmark = `created_at` only vs `(created_at, id)`, buttons Next / Reload / Previous. Output: with a single column, rows are skipped or repeated across pages and Reload shuffles; with the pair, every page is stable. Shows the row-value predicate and the portable rewrite beside it. Fits: sql.ts Phan 5 (extends the existing pagination widget). Closes gap 10.
