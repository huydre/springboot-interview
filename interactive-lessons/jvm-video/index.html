Java có GC rồi, vậy sao ứng dụng vẫn bị OutOfMemoryError?
Hôm nay: JVM Memory & GC.
Phần 1: các vùng nhớ của JVM.
Heap: dùng chung, chứa mọi object, do GC quản lý. Chia thành Young Gen (Eden, Survivor) và Old Gen.
Mỗi thread có stack riêng: mỗi lời gọi method là một frame chứa biến local, tham chiếu.
Metaspace: thông tin class, ở native memory, thay PermGen từ Java 8.
Mỗi vùng đầy ra một lỗi khác nhau.
Phần 2: cái gì nằm ở đâu? quantity là biến local, nằm trong frame trên stack.
Biến order cũng ở stack nhưng chỉ là tham chiếu. Object Order và Item thật nằm trên heap.
Method kết thúc: frame bị xoá. Hai object không còn ai tham chiếu, GC sẽ thu hồi sau.
Stack riêng từng thread nên biến local thread-safe tự nhiên. Heap dùng chung nên cần đồng bộ.
Đệ quy không điểm dừng làm đầy stack: đo được khoảng 42–58 nghìn tầng rồi StackOverflowError.
Phần 3: GC quyết định rác thế nào? Bắt đầu từ GC roots, lần theo mọi tham chiếu.
A, B còn sống vì đi được từ root. C, D trỏ vòng nhau nhưng không root nào tới được: vẫn là rác.
Đã thử: C ⇄ D bị thu hồi thật. Java không dùng reference counting, nên vòng tham chiếu không gây leak.
Ba bước: Mark, Sweep, Compact. Có pha phải dừng mọi thread ứng dụng: stop-the-world.
Phần 4: vòng đời một object. Generational hypothesis: đa số object chết rất trẻ.
Object mới ở Eden. Mỗi Minor GC còn sống thì sang Survivor, tuổi +1. Đủ tuổi thì lên Old Gen.
Phần lớn chết ngay ở Eden, thu hồi rất rẻ. Tạo 2 triệu mảng ngắn hạn: chỉ 5 lần young GC.
Minor GC rẻ, thường xuyên. Full GC dọn cả bộ nhớ heap, pause dài, nên hiếm: xảy ra liên tục là bất thường.
Phần 5: các loại GC. G1 mặc định từ Java 9: chia heap thành region, ưu tiên dọn region nhiều rác.
ZGC: pause dưới 1ms. Parallel: ưu tiên throughput. Serial: một thread.
JDK 21 không cấu hình gì: JVM tự chọn G1.
Câu trả lời an toàn: để mặc định G1, chỉ đổi khi có số liệu cho thấy pause là vấn đề.
Phần 6: các loại OOM. Java heap space: heap đầy, do leak, load quá nhiều dữ liệu, hoặc -Xmx quá nhỏ.
GC overhead limit exceeded: GC chạy gần như liên tục mà thu được rất ít.
Metaspace: quá nhiều class. unable to create native thread: tạo thread không giới hạn. Direct buffer: buffer ngoài heap.
Phần 7: Java vẫn bị memory leak. GC chỉ thu hồi object không còn tham chiếu.
Cache static chỉ put, không xoá. Heap 64 MB: sau 621 entry là OutOfMemoryError.
Leak hay gặp: collection static, cache không giới hạn, ThreadLocal không remove, queue vô hạn.
Phần 8: bẫy trong container. Không cấu hình: heap tối đa = 1/4 bộ nhớ. Máy 16 GB → 4096 MB.
Pod limit 2 GB → heap chỉ 512 MB, dễ OOM dù pod còn RAM trống.
Sửa: -XX:MaxRAMPercentage=75 → heap 1536 MB, chừa chỗ cho phần ngoài heap.
Ngược lại, -Xmx sát limit thì container bị kill: OOMKilled, exit 137.
Phần 9: production bị OOM. Bước 1: xem metrics heap, GC pause. Tăng dần đều là leak, tăng vọt là load quá nhiều.
Bước 2: lấy heap dump. Bước 3: mở bằng Eclipse MAT, xem dominator tree.
Bước 4: object nào chiếm nhiều nhất, ai giữ tham chiếu. Bước 5: sửa code (giới hạn cache, remove ThreadLocal, phân trang).
Công cụ: jcmd, jstat, jstack, JFR, và Spring Boot Actuator.
Stack: biến local, Heap: object · không tới được từ GC root là rác · đa số object chết trẻ · OOM: heap dump, tìm ai giữ tham chiếu.
