## 2. var

```java
var users = new ArrayList<User>();           // compiler tự suy ra kiểu ArrayList<User>
var response = restClient.get().retrieve();  // gọn khi tên kiểu rất dài
for (var entry : map.entrySet()) { ... }
```

- `var` **không** làm Java thành ngôn ngữ kiểu động: kiểu được **xác định lúc compile**, chỉ là bạn không phải viết ra.
- Chỉ dùng cho **biến local** có khởi tạo ngay. Không dùng cho field, tham số method hay kiểu trả về.
- Không dùng được với `var x = null;` hay `var x;` (không có gì để suy kiểu).
- Nên dùng khi kiểu đã **hiển nhiên** từ vế phải. Tránh `var result = service.process();` khi người đọc không đoán được kiểu.

## 3. Text block

```java
String json = """
        {"name": "An", "age": 25}
        """;
// output: {"name": "An", "age": 25}
```

Dùng cho chuỗi nhiều dòng: JSON trong test, câu SQL dài, template. Không cần `\n` và `+` nối chuỗi; phần thụt lề chung được tự động loại bỏ.

## 4. Record

### Hiểu bản chất
`record` là cách khai báo ngắn gọn cho **class chỉ để mang dữ liệu** (data carrier), **immutable**.

```java
public record Money(BigDecimal amount, String currency) {}
```

Một dòng này, compiler tự sinh:
- Field `private final` cho `amount`, `currency`
- Constructor đầy đủ tham số
- Accessor `amount()`, `currency()` (**không** có tiền tố `get`)
- `equals()`, `hashCode()`, `toString()` dựa trên tất cả field

### Validate trong compact constructor

```java
public record Money(BigDecimal amount, String currency) {
    public Money {                                    // compact constructor: không cần lặp lại tham số
        Objects.requireNonNull(currency);
        if (amount.signum() < 0) throw new IllegalArgumentException("amount < 0");
    }
}

new Money(new BigDecimal("-1"), "VND");   // IllegalArgumentException: amount < 0
```

### Giới hạn của record
- **Không kế thừa** class khác (ngầm định đã `extends Record`) và là `final` (không ai kế thừa được nó).
- **Được** implement interface, có method thường và static method.
- Field luôn `final`: không có setter.
- Field kiểu `List` vẫn cần defensive copy (xem [[02.02 - equals, hashCode & String]] mục 6).

### Dùng ở đâu trong dự án Spring
- **DTO** request và response của REST API (Jackson hỗ trợ record từ bản 2.12).
- **Projection** trong Spring Data JPA: `select new com.x.OrderSummary(o.id, o.total) ...`
- `@ConfigurationProperties` (bind cấu hình vào record).
- Value object như `Money`, `Address`.
- **Không** dùng làm **JPA entity**: entity cần constructor không tham số, field có thể thay đổi, và Hibernate cần tạo proxy (kế thừa class), mà record là final.

> **Trả lời mẫu:** "Record là class mang dữ liệu immutable: khai báo một dòng thì compiler sinh field final, constructor, accessor, equals, hashCode và toString. Có thể validate trong compact constructor. Record không kế thừa class khác và là final, nhưng implement được interface. Ở dự án em dùng record cho DTO của API, cho projection trong JPA và cho `@ConfigurationProperties`. Em không dùng record làm JPA entity, vì Hibernate cần constructor rỗng, field sửa được và tạo proxy bằng cách kế thừa class."

## 5. Sealed class và sealed interface

### Hiểu bản chất
`sealed` cho phép **liệt kê chính xác** những class nào được phép kế thừa hoặc implement. Nói cách khác, ta **đóng** hệ phân cấp lại.

```java
public sealed interface Shape permits Circle, Square, Rect {}
public record Circle(double radius) implements Shape {}
public record Square(double side) implements Shape {}
public record Rect(double w, double h) implements Shape {}
```

Class con phải là một trong các dạng: `final`, `sealed` (tiếp tục giới hạn), hoặc `non-sealed` (mở lại cho kế thừa tự do). Record mặc định đã `final`.

### Vì sao hữu ích?
Compiler **biết chắc** có đúng 3 loại `Shape`, nên `switch` trên `Shape` sẽ được **kiểm tra đã đủ case** (exhaustive). Thêm một loại mới như `Triangle` mà quên xử lý thì **lỗi biên dịch** ngay, thay vì lỗi lúc chạy.

Use case thực tế: kết quả thanh toán `sealed interface PaymentResult permits Success, Failed, Pending`, trạng thái đơn hàng, các loại event.

## 6. Pattern matching và switch hiện đại

### Pattern matching cho instanceof (Java 16)

```java
// Cũ
if (obj instanceof String) {
    String s = (String) obj;
    ...
}

// Mới: kiểm tra và ép kiểu trong 1 bước, kèm điều kiện
if (obj instanceof String s && s.length() > 3) {
    System.out.println(s.toUpperCase());   // HELLO
}
```

### Switch expression (Java 14)

```java
int hours = switch (day) {
    case "SAT", "SUN" -> 0;                     // không cần break, không lo "rơi" sang case dưới
    default -> {
        int h = 8;
        yield h;                                // dùng yield khi case có nhiều lệnh
    }
};
```

So với switch cũ: **trả về giá trị**, dùng mũi tên `->` nên **không bị fall-through** (quên `break`), gộp nhiều nhãn bằng dấu phẩy.

### Pattern matching cho switch + record pattern (Java 21)

```java
static double area(Shape s) {
    return switch (s) {
        case Circle c -> Math.PI * c.radius() * c.radius();
        case Square sq -> sq.side() * sq.side();
        case Rect(double w, double h) when w == h -> w * w;   // record pattern + điều kiện "when"
        case Rect(double w, double h) -> w * h;               // tách luôn field của record
    };   // không cần default: Shape là sealed nên compiler biết đã đủ case
}

area(new Rect(2, 3));   // 6.0
area(new Rect(2, 2));   // 4.0
area(new Square(3));    // 9.0
```

Ba thứ phối hợp với nhau: **sealed** (biết đủ các loại) + **record** (dữ liệu rõ ràng) + **pattern matching switch** (xử lý từng loại, compiler kiểm tra thiếu sót). Thay thế được cho chuỗi `if-else instanceof` dài hoặc visitor pattern.

## 7. Sequenced Collections và Virtual Threads

### Sequenced Collections (Java 21)
Các collection có thứ tự (`List`, `Deque`, `LinkedHashSet`, `LinkedHashMap`…) có chung bộ method:

```java
List.of(1, 2, 3).getFirst();                    // 1
new ArrayList<>(List.of(1, 2, 3)).reversed();   // [3, 2, 1]
// còn có getLast(), addFirst(), addLast(), removeFirst(), removeLast()
```

Trước đó phải viết `list.get(list.size() - 1)`, còn `LinkedHashSet` thì phải duyệt hết iterator mới lấy được phần tử cuối; mỗi loại collection một kiểu. Map đi qua `SequencedMap`: `LinkedHashMap` có `firstEntry()`, `lastEntry()`, `putFirst()`, `pollFirstEntry()`, `reversed()`, không có `getFirst()`.

### Virtual Threads (Java 21): giới thiệu
Thread nhẹ do JVM quản lý, tạo được hàng triệu cái, rất hợp cho tác vụ chờ I/O. Spring Boot 3.2+ bật bằng `spring.threads.virtual.enabled=true`. Chi tiết ở **Tuần 3** ([[03 - Concurrency, SQL, REST & Security]]).

> **Trả lời mẫu cho câu "Bạn dùng tính năng Java mới nào?":** "Dự án em chạy Java 17 hoặc 21 vì Spring Boot 3 yêu cầu tối thiểu 17. Em dùng record cho DTO và projection, text block cho JSON trong test và câu SQL dài, switch expression thay cho switch cũ để tránh quên break. Với Java 21 em dùng pattern matching cho switch kết hợp sealed interface để xử lý các loại kết quả thanh toán; compiler kiểm tra giúp em đã xử lý đủ trường hợp. Ngoài ra em biết virtual threads giúp xử lý nhiều request chờ I/O mà không cần chuyển sang reactive."

### Câu hỏi xoáy

**Q1.** Record có thay được Lombok `@Data` không?
> [!success]- Gợi ý trả lời
> Thay được cho **class dữ liệu immutable** (DTO, value object). Không thay được khi cần field sửa được (setter), kế thừa, hoặc JPA entity. Lombok vẫn hữu ích cho `@Builder`, `@Slf4j`, `@RequiredArgsConstructor`.

**Q2.** `var` có làm code chậm hơn hay thành kiểu động không?
> [!success]- Gợi ý trả lời
> Không. `var` chỉ là cú pháp: compiler suy ra kiểu cụ thể lúc biên dịch, bytecode y hệt như khi viết kiểu đầy đủ.

**Q3.** Vì sao switch trên sealed interface không cần `default`?
> [!success]- Gợi ý trả lời
> Compiler biết toàn bộ các class được phép (`permits`), nên kiểm tra được switch đã phủ hết. Nếu thêm `default` thì lại **mất** lợi ích này: khi thêm loại mới, code vẫn compile và rơi vào default một cách âm thầm.
