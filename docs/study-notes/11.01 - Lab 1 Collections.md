## Bài 1: LRU cache bằng LinkedHashMap

### Yêu cầu

Viết class `LruCache<K, V>` có `capacity` cố định. Khi thêm phần tử làm vượt `capacity`, xoá phần tử **lâu nhất chưa được truy cập** (Least Recently Used). Viết ít nhất 5 test:

1. Vượt capacity thì phần tử cũ nhất bị xoá.
2. `get(A)` làm A "trẻ lại", nên phần tử khác bị xoá thay A.
3. `put` đè lên key đã có cũng tính là truy cập, và không làm tăng `size`.
4. `containsKey` có tính là truy cập không? Tự đoán trước, rồi viết test để kiểm chứng.
5. Nếu quên bật `accessOrder` thì cache hoạt động thế nào?

Ràng buộc: không tự viết doubly linked list, dùng `LinkedHashMap`.

### Gợi ý

> [!tip]- Gợi ý
> - `LinkedHashMap` có constructor 3 tham số `(initialCapacity, loadFactor, accessOrder)`. `accessOrder = true` thì mỗi lần `get`/`put` key đã có, entry bị chuyển xuống **cuối** danh sách. Đầu danh sách luôn là phần tử lâu nhất chưa dùng.
> - `LinkedHashMap` gọi `removeEldestEntry(eldest)` sau mỗi `put`. Override nó và trả `true` khi `size() > capacity` thì map tự xoá phần tử đầu.
> - In `keySet()` sau mỗi bước để nhìn thứ tự.

### Kết quả mong đợi

| Test | `keySet()` sau thao tác | Kết quả |
|---|---|---|
| put A, B, C, D (capacity 3) | `[B, C, D]` | PASS |
| put A, B, C, get A, put D | `[C, A, D]` | PASS |
| put A, B, C, put A=100, put D | `[C, A, D]` | PASS |
| capacity 2: put A, B, containsKey A, put C | `[B, C]` | PASS |
| `accessOrder = false`: put A, B, C, get A, put D | `[B, C, D]` | PASS |

```text
Result: 5 passed, 0 failed
```

Hai điều rút ra từ test 4 và 5:
- `containsKey` **không** tính là truy cập: A vẫn bị xoá. Các thao tác đổi thứ tự là `get`, `getOrDefault`, `put`, `putIfAbsent`, `compute...`, `merge`, `replace`.
- Quên `accessOrder = true` thì cache chỉ là **FIFO**: `get(A)` không cứu được A.

### Lời giải

> [!success]- Lời giải
> File đầy đủ: `labs/java-labs/lab1-collections/LruCacheLab.java`
> ```java
> static class LruCache<K, V> extends LinkedHashMap<K, V> {
>     private final int capacity;
>
>     LruCache(int capacity) {
>         super(16, 0.75f, true); // accessOrder = true
>         this.capacity = capacity;
>     }
>
>     @Override
>     protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
>         return size() > capacity; // true thì LinkedHashMap tự xoá phần tử đầu
>     }
> }
> ```
> Test 2 (các test khác tương tự):
> ```java
> LruCache<String, Integer> c = new LruCache<>(3);
> c.put("A", 1); c.put("B", 2); c.put("C", 3);
> c.get("A");          // thứ tự truy cập: B, C, A
> c.put("D", 4);       // B lâu nhất nên bị xoá
> check("get refreshes key: " + c.keySet(),
>         c.containsKey("A") && !c.containsKey("B"));
> ```
> Lưu ý khi nói phỏng vấn: cache này **không thread-safe**. Ngay cả `get` cũng sửa cấu trúc bên trong (chuyển node xuống cuối). Dùng nhiều thread thì bọc bằng `Collections.synchronizedMap(...)`, hoặc dùng thư viện như Caffeine.

## Bài 2: equals có nhưng thiếu hashCode

### Yêu cầu

1. Viết class `BrokenUser` có field `email`, override `equals` theo `email` nhưng **không** override `hashCode`.
2. Tạo 2 object cùng email, `add` cả 2 vào `HashSet`. In ra: `equals`, hai `hashCode` có bằng nhau không, `size()` của set, và `contains(new BrokenUser(cùng email))`.
3. Sửa bằng class `FixedUser` (thêm `hashCode`) và bằng `record`. Kiểm tra lại.

Trước khi chạy, tự đoán `size()` và `contains` ra gì.

### Gợi ý

> [!tip]- Gợi ý
> - `HashSet` bên trong là `HashMap`. Khi `add`, nó tính `hashCode()` để chọn bucket **trước**, chỉ gọi `equals` với các phần tử trong cùng bucket và có cùng hash.
> - Không override `hashCode` thì dùng hash mặc định của `Object`: hai object khác nhau gần như luôn có hash khác nhau.
> - Sửa: `Objects.hash(email)`. `equals` và `hashCode` phải dùng **cùng một tập field**.

### Kết quả mong đợi

| Phiên bản | equals | cùng hashCode | size | contains(bản mới) |
|---|---|---|---|---|
| `BrokenUser` | true | false | **2** | **false** |
| `FixedUser` | true | true | 1 | true |
| `record UserRecord` | true | true | 1 | true |

```text
PASS broken set keeps duplicate (bug reproduced)
PASS fixed set has 1 element
PASS record set has 1 element
Result: 3 passed, 0 failed
```

Chạy 6 lần liên tiếp đều cho cùng kết quả `size=2, contains(new)=false`. Về lý thuyết hai hash mặc định có thể trùng nhau, nhưng xác suất cực nhỏ, nên lỗi này **gần như luôn** tái hiện được.

### Lời giải

> [!success]- Lời giải
> File đầy đủ: `labs/java-labs/lab1-collections/EqualsHashCodeLab.java`
> ```java
> static class FixedUser {
>     final String email;
>
>     FixedUser(String email) { this.email = email; }
>
>     @Override
>     public boolean equals(Object o) {
>         if (this == o) return true;
>         if (!(o instanceof FixedUser other)) return false;
>         return email.equals(other.email);
>     }
>
>     @Override
>     public int hashCode() { return Objects.hash(email); } // cùng field với equals
> }
>
> // Gọn nhất: record tự sinh equals/hashCode theo mọi component
> record UserRecord(String email) { }
> ```
> Ở dự án thật, lỗi này hay gặp khi entity/DTO dùng làm key của `Map` hoặc phần tử của `Set` (ví dụ gom nhóm, loại trùng), và khi dùng Lombok `@EqualsAndHashCode` cho entity JPA (xem [[02.02 - equals, hashCode & String]]).

## Bài 3: ConcurrentModificationException

### Yêu cầu

1. Cho `list = [1, 2, 3, 4, 5, 6]` (`ArrayList`). Dùng **for-each** và gọi `list.remove(n)` để xoá số chẵn. Bắt exception, in tên exception và nội dung list lúc đó.
2. Bẫy: với `[1, 2, 3, 4]`, trong for-each xoá phần tử `3` (áp chót). Có exception không? List cuối cùng là gì?
3. Sửa bằng 3 cách: `removeIf`, `Iterator.remove()`, và tạo list mới bằng stream `filter`.

### Gợi ý

> [!tip]- Gợi ý
> - For-each trên `List` thực chất dùng `Iterator`. `ArrayList` có biến `modCount` tăng mỗi lần sửa cấu trúc; iterator nhớ `expectedModCount`, và trong `next()` thấy lệch thì ném `ConcurrentModificationException`. Cơ chế này gọi là **fail-fast**.
> - Với case áp chót: sau khi xoá, `size` giảm 1, nên `hasNext()` (so `cursor != size`) trả `false` và vòng lặp **dừng sớm** trước khi kịp gọi `next()`.
> - `Iterator.remove()` cập nhật lại `expectedModCount`, nên an toàn.
> - Lưu ý `List<Integer>`: `list.remove(n)` với `n` kiểu `Integer` là `remove(Object)`, còn với `int` là `remove(index)`.

### Kết quả mong đợi

| Cách | Kết quả |
|---|---|
| for-each + `list.remove` | `ConcurrentModificationException`, list lúc đó: `[1, 3, 4, 5, 6]` |
| for-each, xoá phần tử áp chót | **Không** có exception, list: `[1, 2, 4]` |
| `removeIf(n -> n % 2 == 0)` | `[1, 3, 5]` |
| `Iterator.remove()` | `[1, 3, 5]` |
| `stream().filter(...).toList()` | `[1, 3, 5]` |

```text
Result: 5 passed, 0 failed
```

Điểm đáng chú ý:
- Ở case 1, exception ném ra ở lần `next()` **sau** lần xoá đầu tiên, nên list đã kịp mất số `2`. Tức là fail-fast **không rollback** gì cả.
- Ở case 2, số `4` **không bao giờ được duyệt tới** mà không có lỗi gì. Đây là bug âm thầm, nguy hiểm hơn cả exception.

### Lời giải

> [!success]- Lời giải
> File đầy đủ: `labs/java-labs/lab1-collections/ConcurrentModificationLab.java`
> ```java
> // Tái hiện lỗi
> for (Integer n : list) {
>     if (n % 2 == 0) list.remove(n); // remove(Object), modCount tăng
> }
>
> // Sửa 1: removeIf
> a.removeIf(n -> n % 2 == 0);
>
> // Sửa 2: Iterator.remove() khi cần thêm logic trong vòng lặp
> Iterator<Integer> it = b.iterator();
> while (it.hasNext()) {
>     if (it.next() % 2 == 0) it.remove();
> }
>
> // Sửa 3: không sửa list gốc, tạo list mới
> List<Integer> c = data().stream().filter(n -> n % 2 != 0).toList();
> ```
> Ở dự án thật: hay gặp khi duyệt `order.getItems()` để xoá item hết hàng. Với collection trong entity JPA (`orphanRemoval = true`), dùng `removeIf` vẫn đúng và Hibernate sẽ xoá các item bị gỡ.

## Bonus: key mutable bị mất trong HashMap

### Yêu cầu

1. Class `Point { int x; int y; }` có `equals`/`hashCode` đúng theo `x`, `y` nhưng field **không final**.
2. `map.put(new Point(1, 2), "shop A")`, sau đó đổi `key.x = 99`.
3. In `size()`, `get(key)`, `get(new Point(1, 2))`, `containsValue("shop A")`. Giải thích từng kết quả.
4. Sửa bằng key bất biến (`record`).

### Gợi ý

> [!tip]- Gợi ý
> - Entry được đặt vào bucket tính từ hash **lúc put**. Đổi field thì hash mới khác, nhưng entry vẫn nằm ở bucket cũ.
> - `get(key)`: tìm ở bucket theo hash mới, không có. `get(new Point(1, 2))`: tìm đúng bucket cũ, nhưng `equals` so với key đã thành `(99, 2)` nên sai.
> - `containsValue` duyệt toàn bộ map, không dùng hash.

### Kết quả mong đợi

| Phép thử | Kết quả |
|---|---|
| `size()` | 1 |
| `get(key)` | null |
| `get(new Point(1, 2))` | null |
| `containsValue("shop A")` | true |
| Key `record ImmutablePoint` | lấy lại được "shop A" |

```text
PASS entry is lost (bug reproduced)
PASS immutable key works
Result: 2 passed, 0 failed
```

Entry vẫn còn trong map (chiếm bộ nhớ), nhưng không còn cách nào lấy ra bằng key: một kiểu **memory leak** logic.

### Lời giải

> [!success]- Lời giải
> File đầy đủ: `labs/java-labs/lab1-collections/MutableKeyLab.java`
> ```java
> Map<Point, String> map = new HashMap<>();
> Point key = new Point(1, 2);
> map.put(key, "shop A");
> key.x = 99; // hash đổi, entry vẫn ở bucket cũ
>
> // Sửa: key bất biến
> record ImmutablePoint(int x, int y) { }
> ```
> Quy tắc: key của `HashMap` và phần tử của `HashSet` phải **bất biến**, ít nhất là các field tham gia `hashCode`. `String`, `Integer`, `record` (với component bất biến) là lựa chọn an toàn.

## Câu hỏi phỏng vấn liên quan

**Q1.** Cài LRU cache thế nào? Độ phức tạp của `get`/`put`?
> [!success]- Gợi ý trả lời
> Cách nhanh: extends `LinkedHashMap` với `accessOrder = true` và override `removeEldestEntry` trả `size() > capacity`. Bên trong là HashMap cộng doubly linked list, nên `get`/`put` đều O(1). Nếu bị yêu cầu tự cài: `HashMap<K, Node>` cộng doubly linked list tự viết, `get` thì chuyển node về đầu, `put` vượt capacity thì xoá node cuối. Em đã viết test và thấy `containsKey` không làm đổi thứ tự, còn quên `accessOrder` thì cache thành FIFO. Cache này không thread-safe; production em dùng Caffeine.

**Q2.** Override `equals` mà không override `hashCode` thì sao?
> [!success]- Gợi ý trả lời
> Vi phạm contract: hai object `equals` bằng nhau phải có cùng `hashCode`. HashSet/HashMap tìm bucket bằng hash trước, nên hai object "bằng nhau" rơi vào hai bucket khác nhau. Em đã chạy thử: add 2 user cùng email vào HashSet thì `size` là 2 và `contains` một bản mới cùng email trả `false`. Sửa bằng `Objects.hash` trên cùng các field dùng trong `equals`, hoặc dùng record.

**Q3.** `ConcurrentModificationException` xảy ra khi nào? Chỉ trong đa luồng thôi à?
> [!success]- Gợi ý trả lời
> Không, phần lớn xảy ra ngay trong **một thread**: sửa cấu trúc collection (add/remove) trong lúc đang duyệt bằng iterator hoặc for-each. Iterator fail-fast so `modCount` với `expectedModCount`, lệch thì ném lỗi. Sửa bằng `removeIf`, `Iterator.remove()`, hoặc tạo collection mới. Có một bẫy: xoá phần tử áp chót thì không có exception mà phần tử cuối bị bỏ qua âm thầm, em đã tái hiện được với list `[1, 2, 3, 4]`. Đa luồng thì dùng `CopyOnWriteArrayList` hoặc `ConcurrentHashMap`, iterator của chúng không ném CME.

**Q4.** Vì sao key của HashMap nên bất biến?
> [!success]- Gợi ý trả lời
> Vì vị trí bucket được tính từ hash lúc `put`. Đổi field tham gia `hashCode` sau khi put thì `get` bằng chính key đó tìm sai bucket, còn `get` bằng key giá trị cũ thì đúng bucket nhưng `equals` sai. Em thử thì `size` vẫn là 1, `containsValue` vẫn true, nhưng mọi `get` đều null: entry bị "mất" và chiếm bộ nhớ. Nên dùng `String`, wrapper, hoặc record làm key.
