## 1. == và equals()

### Hiểu bản chất
- `==` so sánh **giá trị nằm trong biến**:
  - Biến primitive (`int`, `long`…): giá trị là con số, nên `==` so sánh **số**.
  - Biến object: giá trị là **địa chỉ (tham chiếu)**, nên `==` hỏi "hai biến có **trỏ tới cùng một object** không?".
- `equals()` là method, hỏi "hai object có **bằng nhau về nội dung** không?". Ý nghĩa "bằng nhau" do **class tự định nghĩa**.
- Nếu class **không override**, `Object.equals()` mặc định chính là `==`.

### Code minh hoạ

```java
String a = new String("java");
String b = new String("java");
System.out.println(a == b);        // false: 2 object khác nhau trên heap
System.out.println(a.equals(b));   // true: String override equals để so nội dung
```

### Bẫy 1: Integer cache

```java
Integer x = 127, y = 127;
Integer m = 128, n = 128;
System.out.println(x == y);        // true
System.out.println(m == n);        // false
System.out.println(m.equals(n));   // true
```

**Vì sao?** Autoboxing `Integer x = 127` thực chất gọi `Integer.valueOf(127)`. Method này **trả về object có sẵn trong cache** cho các giá trị từ **-128 đến 127**, nên `x` và `y` cùng trỏ một object. Từ 128 trở đi, mỗi lần gọi tạo object mới. `Long`, `Short`, `Byte`, `Character` (0–127) cũng có cache tương tự.

Bug thật hay gặp: so sánh hai `Long id` lấy từ DB bằng `==`. Code chạy đúng khi test với id nhỏ, rồi sai trên production khi id > 127.

### Bẫy 2: NullPointerException do unboxing

```java
Integer count = null;          // ví dụ lấy từ Map hay DB và không có giá trị
if (count == 0) { ... }        // ❌ NullPointerException
```

Khi so sánh `Integer` với `int`, Java **unbox** `Integer` thành `int` bằng cách gọi `count.intValue()`, mà `count` đang là `null`. Cách an toàn: `Objects.equals(count, 0)`, hoặc kiểm tra `null` trước.

### Bẫy 3: gọi equals trên biến có thể null

```java
status.equals("ACTIVE")          // ❌ NPE nếu status null
"ACTIVE".equals(status)          // ✓ hằng số đứng trước
Objects.equals(status, "ACTIVE") // ✓ an toàn cả 2 phía
```

> **Trả lời mẫu:** "`==` so sánh giá trị nằm trong biến: với primitive là con số, với object là tham chiếu, tức hai biến có trỏ cùng một object không. `equals()` so sánh nội dung theo cách class định nghĩa, và nếu không override thì nó chính là `==`. Bẫy hay gặp là Integer cache: `Integer` từ -128 đến 127 được cache nên `==` cho true, còn 128 thì false. Vì vậy em luôn so sánh wrapper như `Long id` bằng `equals` hoặc `Objects.equals`, và cẩn thận NPE khi unboxing một `Integer` null."

### Câu hỏi xoáy

**Q1.** `Integer.valueOf(100) == Integer.valueOf(100)` và `new Integer(100) == new Integer(100)` cho kết quả gì?
> [!success]- Gợi ý trả lời
> `true` và `false`. `valueOf` dùng cache, còn `new` luôn tạo object mới. Constructor `new Integer(...)` đã deprecated (đánh dấu for removal), nên dùng `valueOf` hoặc autoboxing.

**Q2.** Có thay đổi được khoảng cache của Integer không?
> [!success]- Gợi ý trả lời
> Có thể nâng giới hạn trên bằng tham số JVM `-XX:AutoBoxCacheMax=<n>`. Nhưng đừng bao giờ dựa vào cache để so sánh: luôn dùng `equals`.

## 2. Contract giữa equals() và hashCode()

### Hiểu bản chất

`HashMap`/`HashSet` tìm phần tử theo **2 bước**:
1. Dùng `hashCode()` để tìm **bucket** (ngăn chứa).
2. Trong bucket đó, dùng `equals()` để tìm **đúng phần tử**.

Vì vậy hai method phải **thống nhất** với nhau. Đó là **contract**:

| Quy tắc | Ý nghĩa |
|---|---|
| `a.equals(b)` ⇒ `a.hashCode() == b.hashCode()` | **Bắt buộc**. Nếu không, hai object "bằng nhau" rơi vào hai bucket khác nhau và không bao giờ gặp nhau để so `equals` |
| `hashCode` bằng nhau ⇏ `equals` | Hai object khác nhau **được phép** trùng hashCode (gọi là **collision**). Chỉ làm chậm, không làm sai |
| `hashCode()` gọi nhiều lần phải trả cùng giá trị | Miễn là các field dùng trong `equals` không đổi |

Năm tính chất của `equals()`:

| Tính chất | Nghĩa |
|---|---|
| Phản xạ | `x.equals(x)` luôn `true` |
| Đối xứng | `x.equals(y)` ⇔ `y.equals(x)` |
| Bắc cầu | `x.equals(y)` và `y.equals(z)` ⇒ `x.equals(z)` |
| Nhất quán | Gọi nhiều lần cho cùng kết quả nếu object không đổi |
| Với null | `x.equals(null)` luôn `false` (không ném NPE) |

### Code minh hoạ: override equals mà quên hashCode

```java
class UserNoHash {
    private final String email;
    UserNoHash(String email) { this.email = email; }

    @Override public boolean equals(Object o) {
        return o instanceof UserNoHash u && email.equals(u.email);
    }
    // ❌ quên hashCode → dùng Object.hashCode (khác nhau với mỗi object)
}

Set<UserNoHash> set = new HashSet<>();
set.add(new UserNoHash("an@x.com"));
set.add(new UserNoHash("an@x.com"));
System.out.println(set.size());                                       // 2 ❌ (kỳ vọng 1)
System.out.println(set.contains(new UserNoHash("an@x.com")));         // false ❌
```

Hai object "bằng nhau" theo `equals` nhưng hashCode khác nhau, nên nằm ở 2 bucket khác nhau. `HashSet` không bao giờ gọi `equals` giữa chúng, dẫn tới **trùng lặp** và **tìm không thấy**.

> **Trả lời mẫu:** "HashMap và HashSet dùng `hashCode` để tìm bucket, rồi dùng `equals` để tìm đúng phần tử trong bucket. Vì vậy contract bắt buộc: hai object `equals` nhau thì phải có cùng `hashCode`; ngược lại hashCode trùng nhau thì không cần equals, đó chỉ là collision. Nếu override `equals` mà quên `hashCode`, hai object bằng nhau sẽ rơi vào hai bucket khác nhau: `HashSet` chứa trùng và `contains` trả về false. Em thường dùng `record`, hoặc để IDE/Lombok sinh cả hai method cùng lúc từ cùng một tập field."

### Câu hỏi xoáy

**Q1.** Viết `hashCode()` luôn `return 1;` thì có sai không?
> [!success]- Gợi ý trả lời
> **Không vi phạm contract** (object bằng nhau vẫn cùng hashCode), nên kết quả vẫn đúng. Nhưng mọi phần tử dồn vào **một bucket**, nên HashMap thoái hoá từ O(1) xuống O(n), hoặc O(log n) nếu bucket được treeify. Hiệu năng rất tệ.

**Q2.** Override `hashCode` mà không override `equals` thì sao?
> [!success]- Gợi ý trả lời
> Object có nội dung giống nhau sẽ cùng bucket, nhưng `equals` mặc định vẫn so tham chiếu, nên vẫn bị coi là khác nhau. `HashSet` vẫn chứa trùng. Hai method luôn phải đi cùng nhau.

## 3. Viết equals() và hashCode() đúng cách

### Cách viết tay chuẩn

```java
public final class User {
    private final String email;
    private final String name;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                                // 1. cùng object
        if (o == null || getClass() != o.getClass()) return false; // 2. null hoặc khác kiểu
        User other = (User) o;
        return Objects.equals(email, other.email);                 // 3. so field nghiệp vụ (null-safe)
    }

    @Override
    public int hashCode() {
        return Objects.hash(email);                                // dùng ĐÚNG các field đã dùng trong equals
    }
}
```

**Chọn field nào?** Field xác định "danh tính" của object. Ví dụ `User` bằng nhau khi trùng email, không cần trùng `name`. Field trong `hashCode` phải là **tập con** của field trong `equals`, và thường là đúng bằng.

### `getClass()` hay `instanceof`?
- `getClass() != o.getClass()`: class con và class cha **không bao giờ** bằng nhau. An toàn cho tính **đối xứng**.
- `instanceof`: cho phép class con bằng class cha, nhưng dễ phá tính đối xứng nếu class con thêm field vào `equals`. Nên dùng khi class là `final`, hoặc khi hợp đồng bằng nhau được định nghĩa ở class cha (ví dụ `List`: mọi `List` có cùng phần tử theo cùng thứ tự đều bằng nhau).

### Cách ngắn gọn: record (Java 16+)

```java
public record Money(BigDecimal amount, String currency) {}
// Tự sinh equals/hashCode/toString theo TẤT CẢ field
```

### Lombok
- `@EqualsAndHashCode(onlyExplicitlyIncluded = true)` + `@EqualsAndHashCode.Include` trên field danh tính.
- **Cẩn thận với JPA entity:** không dùng `@Data`, vì nó sinh equals/hashCode từ mọi field, kể cả lazy association. Chi tiết ở [[05 - Transaction & JPA]] câu 21.

### Bẫy: field trong hashCode bị thay đổi sau khi đã bỏ vào HashSet/HashMap

Object sẽ "mất tích" trong collection. Phần này học kỹ ở [[02.04 - HashMap Internals]].

## 4. String immutable và String pool

### Hiểu bản chất
- **Immutable**: sau khi tạo, nội dung String **không bao giờ đổi**. `toUpperCase()`, `concat()`, `replace()`… đều **trả về String mới**.
- **String pool**: vùng chứa các String **literal** (chuỗi viết trực tiếp trong code). Hai literal giống nhau dùng **chung một object**. Từ Java 7, pool nằm trong **heap**.

### Vì sao String được thiết kế immutable?

| Lý do | Giải thích |
|---|---|
| **String pool** | Nhiều biến cùng trỏ một object; nếu sửa được thì một chỗ sửa sẽ làm hỏng mọi chỗ khác |
| **Thread-safe** | Không ai sửa được, nên chia sẻ giữa các thread mà không cần lock |
| **Cache hashCode** | Tính hashCode một lần rồi lưu lại, nên làm key `HashMap` rất nhanh |
| **Bảo mật** | Đường dẫn file, URL, tên class được kiểm tra xong thì không thể bị đổi sau đó |

### Code minh hoạ

```java
String s1 = "java";                  // literal → lấy từ pool
String s2 = "java";                  // cùng object trong pool
String s3 = new String("java");      // luôn tạo object MỚI trên heap

System.out.println(s1 == s2);            // true
System.out.println(s1 == s3);            // false
System.out.println(s1 == s3.intern());   // true: intern() trả về bản trong pool

String ab = "a" + "b";               // hằng số lúc compile → compiler gộp thành "ab" → vào pool
System.out.println(ab == "ab");      // true

String a = "a";
String runtime = a + "b";            // nối lúc RUNTIME (a là biến) → object mới, không vào pool
System.out.println(runtime == "ab");      // false
System.out.println(runtime.equals("ab")); // true
```

**Bài học:** đừng bao giờ dùng `==` để so sánh String. Kết quả phụ thuộc vào việc chuỗi được tạo **lúc compile hay lúc runtime**.

### `new String("java")` tạo mấy object?
**Tối đa 2**: một literal `"java"` trong pool (nếu pool chưa có) và một object mới trên heap.

> **Trả lời mẫu:** "String là immutable: mọi thao tác 'sửa' đều tạo String mới. Lý do: để String pool chia sẻ an toàn giữa nhiều biến, để thread-safe mà không cần lock, để cache được hashCode giúp làm key HashMap nhanh, và để bảo mật khi String là đường dẫn hay URL. Literal giống nhau dùng chung một object trong pool, còn `new String` luôn tạo object mới. Vì kết quả `==` phụ thuộc chuỗi được tạo lúc compile hay runtime, em luôn so String bằng `equals`."

### Câu hỏi xoáy

**Q1.** Nếu String immutable thì `s = s + "x"` hoạt động thế nào?
> [!success]- Gợi ý trả lời
> Object cũ không đổi. Phép nối tạo **String mới**, và biến `s` được gán tham chiếu tới object mới đó. Object cũ (nếu không còn ai tham chiếu) sẽ bị GC thu hồi.

**Q2.** Có cách nào sửa nội dung một String không?
> [!success]- Gợi ý trả lời
> Về nguyên tắc là không. Reflection có thể can thiệp vào mảng bên trong ở các bản Java cũ, nhưng từ Java 9+ với module system thì bị chặn mặc định, và đó luôn là hack nguy hiểm.

**Q3.** Vì sao nên lưu mật khẩu trong `char[]` thay vì `String`?
> [!success]- Gợi ý trả lời
> String immutable và có thể nằm trong pool hoặc heap rất lâu tới khi GC chạy, nên có thể lộ ra khi người khác lấy heap dump. `char[]` ghi đè được (`Arrays.fill(pwd, '0')`) ngay sau khi dùng xong.

## 5. String, StringBuilder, StringBuffer

| | `String` | `StringBuilder` | `StringBuffer` |
|---|---|---|---|
| Thay đổi được | ✗ | ✓ | ✓ |
| Thread-safe | ✓ (vì immutable) | ✗ | ✓ (method `synchronized`) |
| Tốc độ khi nối nhiều | Chậm (tạo object mới mỗi lần) | **Nhanh nhất** | Chậm hơn Builder (tốn chi phí lock) |
| Dùng khi | Hầu hết trường hợp | Nối chuỗi trong **vòng lặp** | Hầu như không cần dùng nữa |

```java
// ❌ Mỗi vòng lặp tạo 1 String mới → O(n²) ký tự bị copy
String result = "";
for (String item: items) result += item + ",";

// ✓
StringBuilder sb = new StringBuilder();
for (String item: items) sb.append(item).append(',');
String result = sb.toString();

// ✓ Gọn hơn nữa
String result = String.join(",", items);
```

Lưu ý: nối String trong **một biểu thức đơn** (`"Hello " + name + "!"`) thì cứ viết `+`, vì compiler đã tối ưu (Java 9+ dùng `StringConcatFactory`). Chỉ cần `StringBuilder` khi nối **trong vòng lặp**.

## 6. Viết một immutable class

### Quy tắc
1. Class `final`, để không ai kế thừa rồi thêm hành vi "sửa được".
2. Mọi field `private final`.
3. **Không có setter.** Method "thay đổi" thì trả về **object mới** (giống `String`, `BigDecimal`, `LocalDate`).
4. **Defensive copy** với field mutable (`List`, `Date`, mảng): copy khi **nhận vào** và không trả ra tham chiếu gốc.

### Code minh hoạ

```java
public final class Order {
    private final String id;
    private final List<String> items;

    public Order(String id, List<String> items) {
        this.id = id;
        this.items = List.copyOf(items);      // copy khi nhận vào → bên ngoài sửa list gốc không ảnh hưởng
    }

    public List<String> getItems() { return items; }   // List.copyOf đã unmodifiable → trả thẳng an toàn

    public Order addItem(String item) {                // "thay đổi" = tạo object mới
        List<String> newItems = new ArrayList<>(items);
        newItems.add(item);
        return new Order(id, newItems);
    }
}

List<String> source = new ArrayList<>(List.of("book"));
Order order = new Order("O1", source);
source.add("hack");                         // sửa list gốc
System.out.println(order.getItems());       // [book]: không bị ảnh hưởng
order.getItems().add("x");                  // ❌ UnsupportedOperationException
```

### Record cũng cần defensive copy

```java
public record OrderRecord(String id, List<String> items) {
    public OrderRecord {                    // compact constructor
        items = List.copyOf(items);         // nếu thiếu dòng này, record vẫn "lộ" list mutable ra ngoài
    }
}
```

### Vì sao immutable tốt?
- **Thread-safe** mà không cần lock.
- An toàn làm **key HashMap** hay phần tử `HashSet`, vì hashCode không bao giờ đổi.
- Dễ suy luận và debug: object không bị ai đó âm thầm sửa ở nơi khác.
- Hợp làm **DTO**, value object (`Money`, `Address`).

> **Trả lời mẫu:** "Để viết immutable class, em đặt class `final`, field `private final`, không có setter; method thay đổi thì trả về object mới, giống `BigDecimal` hay `LocalDate`. Quan trọng nhất là defensive copy với field mutable như `List`: copy khi nhận vào bằng `List.copyOf` và không trả ra tham chiếu gốc. Record cũng cần làm việc này trong compact constructor. Lợi ích là thread-safe không cần lock, an toàn làm key HashMap, và dễ suy luận. Em hay dùng record cho DTO và value object."

### Câu hỏi xoáy

**Q1.** Field là `final List<String> items` thì object đã immutable chưa?
> [!success]- Gợi ý trả lời
> **Chưa**. `final` chỉ cấm **gán lại** biến `items` sang list khác; nội dung list vẫn `add`/`remove` được. Cần thêm defensive copy và list unmodifiable.

**Q2.** `Collections.unmodifiableList(list)` có đủ để làm field immutable không?
> [!success]- Gợi ý trả lời
> Không hẳn. Nó chỉ là **view**: nếu ai đó còn giữ tham chiếu tới `list` gốc và sửa nó, view cũng đổi theo. `List.copyOf()` tạo **bản copy** độc lập nên an toàn hơn.
